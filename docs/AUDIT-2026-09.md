# Audit IO CAR — 19 septembre 2026

Audit demandé sur quatre angles : risques métier, sécurité, robustesse
technique, qualité du code. Chaque constat ci-dessous a été vérifié dans le
code, pas déduit. Les points écartés après vérification sont signalés comme
tels — une fausse alerte coûte autant qu'un vrai défaut manqué.

Contexte à garder en tête : un client payant en production, un développeur
seul, Supabase en plan gratuit (aucune sauvegarde restaurable côté
hébergeur), Vercel en plan Hobby (12 fonctions serverless maximum).

---

## 0. LA CAUSE COMMUNE — Les helpers transforment un échec en donnée plausible

Les constats qui suivent ne sont pas des problèmes indépendants. Ils
découlent d'une seule décision, prise une fois dans les helpers d'accès aux
données et répétée à l'identique dans IO BILL : **quand une requête échoue,
le helper ne le dit pas — il renvoie une valeur qui ressemble à un résultat
normal.**

```js
async upsert(...) { ... return r.ok ? r.json() : null; }   // échec → null, sans lever
async update(...) { ... return r.ok ? r.json() : null; }   // échec → null, sans lever
async delete(...) { await fetch(...); }                    // ne regarde même pas r.ok
```

Et au chargement, `.catch(() => setData([]))` : un échec devient une liste
vide.

Autrement dit, l'application ne distingue jamais « il n'y a rien » de « je
n'ai pas réussi à savoir ». Les deux se présentent de la même façon, avec la
même assurance.

C'est ce qui explique le point 2 ci-dessous, et c'est ce qui rend inopérant
le log `❌ upsert FAIL` du livre de police : il attend une exception qui ne
vient jamais.

### Pourquoi c'est une bonne nouvelle

Le correctif est concentré. Il ne s'agit pas de reprendre tous les appels,
mais de faire dire la vérité à **trois fonctions** — lever une erreur
explicite sur `!r.ok` — puis de reprendre les écrans qui comptaient sur le
silence.

Priorité évidente : le livre de police, parce que c'est le seul endroit où
une perte silencieuse a des conséquences légales.

## 1. CRITIQUE — Le schéma de la base n'existe nulle part dans le dépôt

Les quatre fichiers de `supabase/` sont des correctifs : sécurité, purge du
livre de police, verrou des avoirs, pont IO BILL. **Aucun ne contient de
`CREATE TABLE`.**

```
$ grep -i "create table" supabase/*.sql
(aucun résultat)
```

Les tables `garages`, `vehicles`, `orders`, `clients`, `livre_police`,
`support_tickets`, `ticket_messages` — avec leurs contraintes, leurs index,
leurs politiques RLS et leurs déclencheurs — n'existent que dans la base
vivante.

**Pourquoi c'est le point le plus grave.** Les sauvegardes automatiques
mises en place le 13 septembre écrivent les **lignes** des tables, pas leur
structure. En cas de perte du projet Supabase — suppression accidentelle,
incident chez l'hébergeur, compte fermé — tu disposerais d'un JSON de
données sans aucun moyen de reconstruire le schéma qui les accueille. Ni les
tables, ni les politiques RLS, ni les fonctions `consume_plate_lookup` /
`purge_livre_police_expired`, ni les déclencheurs.

Or le livre de police est soumis à une obligation de conservation de dix ans
(art. L123-22 du Code de commerce pour les livres, art. R.321-3 du Code
pénal pour le registre lui-même). Une sauvegarde qu'on ne sait pas restaurer
ne remplit pas cette obligation.

**Correctif** : exporter le schéma complet de la base de production vers
`supabase/00_schema.sql` et le versionner. Supabase permet de le faire en
une commande. C'est une heure de travail pour transformer une demi-protection
en protection réelle.

## 2. CRITIQUE — Les écritures échouent en silence

`useSupabaseTable` persiste les modifications en « optimiste » : l'état React
est mis à jour immédiatement, et l'écriture Supabase part sans être attendue.

```js
sb.upsert(token, table, { id, garage_id: garageId, data: fields })
  .then(() => { if (table === "livre_police") console.log(`[LP Sync] ✅ upsert OK: ${id}`); })
  .catch(err => console.error(`[LP Sync] ❌ upsert FAIL: ${id}`, err));
```

Le problème n'est pas l'optimisme, c'est que **l'échec est indétectable** :

```js
async upsert(token, table, data) {
  const r = await fetch(...);
  return r.ok ? r.json() : null;   // ← ne lève JAMAIS
}
```

`sb.upsert` ne lève pas d'exception quand PostgREST refuse. Il renvoie
`null`, dans une promesse **résolue**. Le `.catch` ne se déclenche donc que
sur une panne réseau au niveau de `fetch` — pas sur un 400, un 401, un 403,
un 409 ni un 500. Autrement dit, le log `❌ upsert FAIL` qui a visiblement
été ajouté pour diagnostiquer les problèmes de synchronisation du livre de
police **ne se déclenche pas dans le cas le plus fréquent**.

Conséquence concrète : une entrée du livre de police refusée par la base
disparaît sans laisser de trace. Pas d'erreur à l'écran, pas de log console,
rien. L'utilisateur voit son entrée dans la liste — elle est dans l'état
React — et la croit enregistrée. Elle n'existera plus au rechargement
suivant.

Deux variantes du même défaut :

- `sb.delete(token, table, id).catch(() => {})` — la suppression ne vérifie
  même pas `r.ok`, et son échec est explicitement ignoré. La ligne disparaît
  de l'écran et revient au rechargement.
- Au chargement, `.catch(() => setData([]))` affiche une **liste vide** en
  cas d'échec. Une coupure réseau passagère fait donc croire à l'utilisateur
  que sa flotte a été effacée.

**Correctif** : faire vérifier `r.ok` par les helpers et lever une erreur
explicite, remonter les échecs d'écriture à l'écran plutôt qu'en console, et
distinguer « liste vide » de « chargement échoué ».

## 3. MOYEN — Une fonction serverless morte occupe un des douze slots

`api/report-plate-usage.js` ne fait rien :

```js
export default async function handler(req, res) {
  if (req.method !== 'POST') return res.status(405).end();
  const { garageId, quantity } = req.body || {};
  if (!garageId || !quantity) return res.status(400).json({ error: 'Missing params' });
  console.log(`Plate usage: garage=${garageId}, qty=${quantity}`);
  res.status(200).json({ ok: true });
}
```

Elle ne touche ni la base, ni Stripe. Elle n'est appelée de nulle part —
aucune occurrence dans `src/` ni dans `api/`. Le report réel de la
consommation se fait dans `api/lookup-plate.js`, via `billing.meterEvents`.

Absence d'authentification : sans effet, puisque l'endpoint n'écrit rien.
Mais il **occupe un des douze slots** du plan Hobby. IO CAR est à 11 sur 12 ;
la supprimer ramène à 10 et rend une marge de manœuvre qui a déjà manqué une
fois, quand l'ajout du cron de sauvegarde a cassé le déploiement d'IO BILL.

## 4. MOYEN — La facturation des plaques en dépassement peut céder en silence

Chaîne à quatre maillons, dont trois cèdent sans bruit :

1. **La ligne « consommation » n'est ajoutée qu'au checkout**, et seulement
   si la variable d'environnement de la bonne périodicité est renseignée
   (`STRIPE_METERED_PRICE_ID` au mois, `STRIPE_METERED_PRICE_ANNUAL` à
   l'année). Sinon, l'abonnement part sans elle — choix délibéré et
   raisonnable — mais **renseigner la variable plus tard ne répare pas les
   abonnements déjà créés**.
2. Le report exige `garage.stripe_customer_id`. Un garage créé à la main ou
   migré ne remonte rien.
3. `event_name: 'api_requests'` doit correspondre exactement à la meter
   configurée côté Stripe. Une divergence ne produit aucune erreur.
4. L'échec est capturé et journalisé sans bloquer — bon choix, mais la
   recherche non facturée ne laisse aucune trace dans l'application.

À quoi s'ajoute un défaut d'affichage : l'interface annonce « X € HT à
facturer » à partir du seul compteur local, sans savoir si l'abonnement
porte réellement la ligne de consommation. L'abonné peut donc voir un montant
qui ne lui sera jamais facturé.

**Vérification** : dans Stripe, un abonnement qui facture réellement les
dépassements a **deux lignes**. Une seule ligne = aucun dépassement facturé.

## 5. FAIBLE — Sortie de build versionnée

Dix fichiers de `dist/` restent suivis par git alors que `.gitignore` liste
le dossier. Un `.gitignore` n'a aucun effet sur un fichier déjà suivi : chaque
branche qui reconstruit recommite le bundle, et deux branches parallèles
entrent en conflit. C'est ce qui a bloqué le merge de la PR #47.

`git rm --cached -r dist/` règle le point définitivement, sans rien supprimer
sur le disque ni changer quoi que ce soit chez Vercel, qui reconstruit depuis
les sources.

## 6. QUALITÉ — Un fichier de 13 389 lignes

`src/App.jsx` porte l'application entière : routage, état, appels réseau,
tous les écrans, et le CSS en chaîne de caractères. Il grossit à chaque
fonctionnalité.

Ce n'est pas un défaut en soi — le fichier est lisible, bien commenté, et le
commentaire y explique presque toujours *pourquoi* plutôt que *quoi*, ce qui
est rare et précieux. Mais il a deux effets mesurables :

- **Les conflits de fusion.** Deux branches touchant deux fonctionnalités
  sans rapport modifient le même fichier. C'est arrivé entre les PR #47 et
  #48.
- **Le coût de relecture.** Chaque modification demande de retrouver son
  contexte dans 13 000 lignes.

Aucune urgence. Mais si l'occasion se présente, extraire les zones stables et
autonomes — le générateur de PDF, le livre de police, les helpers de calcul —
réduirait la surface de collision sans rien réécrire.

## 7. Absence de tests et d'intégration continue

Aucun fichier de test, aucun workflow GitHub Actions. La seule vérification
avant publication est `npm run build`, qui n'attrape que les erreurs de
syntaxe et d'import.

Trois régressions de cette semaine seraient passées au travers d'un build
réussi : le régime TVA par défaut d'un dépôt-vente, la chaîne de hachage
cassée par une migration, et la modale rendue dans le flux de la page.

Vu le contexte — un développeur seul, pas de temps pour une suite complète —
la piste la plus rentable n'est pas de tout tester, mais de couvrir les rares
fonctions de **calcul pur** dont une erreur coûte cher : `prixAchatReel`,
`getQuotaStatus`, la répartition TVA. Elles n'ont aucune dépendance, se
testent en quelques lignes, et ce sont elles qui produisent des chiffres
faux sans rien casser visiblement.

## Points vérifiés et écartés

- **La clé Supabase en dur dans `src/App.jsx`** est la clé `anon`
  (vérifié en décodant le JWT : `role: anon`). Elle est publique par
  conception et sans danger tant que RLS est actif. Ce n'est pas une fuite.
- **Aucun `.env` n'a jamais été versionné**, sur toute l'histoire du dépôt.
- **Aucune vulnérabilité** signalée par `npm audit` sur les dépendances de
  production.
- **Aucun `dangerouslySetInnerHTML`**, aucun `eval`, aucun `new Function`.
- Les endpoints `admin`, `images`, `iobill-bridge`, `lookup-plate`,
  `public`, `ticket`, `customer-portal` **vérifient tous l'authentification**.
  `create-checkout-session` est public par nécessité — on souscrit avant
  d'avoir un compte.
